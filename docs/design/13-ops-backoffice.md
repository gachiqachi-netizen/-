## 1. 订单状态：三方是否一致

### 1.1 对照表

后端有五组状态（订单、支付、履约、物流、售后）。用户和后台各看一个合成的词。

| 实际情况（后端五组状态） | 用户看到（06 §3.1） | 后台看到（12 §4） | 一致吗 |
|---|---|---|---|
| 下单了，没付款 | 待支付 | 待支付 | 一致 |
| 付款了，还没开始做（履约 unfulfilled） | 06 没有这一行，会落到“处理中” | 待制作 | **不一致**：用户应看到“制作中” |
| 制作中 / 待发货 | 制作中 / 待发货 | 制作中、质检不通过 / 待发货 | 一致（质检不通过只给后台看，用户仍是“制作中”） |
| 已发货、运输中 | 运输中 | 已发货 | 一致（措辞不同，各自合适） |
| 物流异常、已退回 | 物流有点问题 | 物流异常 | 一致 |
| 物流已签收，用户没确认 | 已签收 + 主按钮“确认收货” | 已发货 | **不一致**，见 1.2 第 1 条 |
| 订单已完成 | 已完成 | 已完成 | 一致 |
| 取消 / 关闭 | 已取消 | 已取消 / 已关闭 | 一致 |
| 退款中 / 已退款 / 退款失败 | 退款中 / 已退款 / 退款遇到问题 | 售后中（详情里写） | 一致 |
| 有售后 | 售后处理中 / 已完成 / 未通过 | 售后中 | 一致 |

### 1.2 对不上的地方

| # | 问题 | 现在后端怎样 | 影响 | 建议 |
|---|---|---|---|---|
| S1 | **签收后用户点不了“确认收货”** | 只有物流是“已发货 / 运输中”时才给 `confirm_receipt`；后台把物流改成“已签收”后，这个动作就没了 | 订单永远停在“已签收”，变不成“已完成”（06 里的 B-O1 一直没做） | 物流“已签收”时也允许确认收货；再加“签收 7 天后自动确认收货”（需后端，定时任务） |
| S2 | 用户不能自己申请售后、退款 | 售后单只能后台建（`create_after_sale` 是后台用的），用户动作里没有 `request_after_sale` | 小程序“申请退款”“申请售后”两个入口点了没有接口 | 补用户申请售后接口（B5） |
| S3 | 售后类型三方不一样 | 后端：仅退款、退货退款、补发 | 小程序设计有：仅退款、退货退款、补寄配件、改手围重串、拒收后退款 | 统一成五种：仅退款、退货退款、补寄配件、改手围重串、拒收后退款（需后端改 `AFTER_SALE_TYPES`，“补发”改名“补寄配件”） |
| S4 | 发货前改地址没有接口 | 用户和后台都改不了收货地址 | 小程序“修改地址”和客服代改都做不了 | 加“发货前改地址”：用户在发货前可改，后台随时可改并记录（需后端） |
| S5 | “待确认 → 已确认”要后台手动点 | 订单状态默认“待确认”，后台点“确认”才变“已确认”；用户只能在“待确认”时取消 | 后台点过确认后，没付款的用户就取消不了了；“确认”这一步也没有业务含义 | 去掉手动确认：付款成功时自动变“已确认”；没付款前用户随时能取消 |
| S6 | 没有任何订单能进入制作 | 支付没接；“未付款不能开始制作”；付款状态只能由支付回调改 | 支付开通前收到的单只能一直“待支付” | **已处理：加了模拟支付通道**（见 1.3）。开发和体验环境走模拟付款，整条链路能测；商户号下来后只换支付这一层 |
| S7 | 用户订单进度条没有数据 | 用户接口现在给的是去掉操作人的 `statusHistory`（五组原始记录） | 06 要的“下单 → 制作 → 运输 → 签收”四步和时间，前端要自己从原始记录拼 | 后端直接给 `progress: [{step, at}]`（06 的 B-O3 后半部分） |
| S8 | 两套合成规则写在两处 | 用户主状态（06 §3.1）在小程序算，后台状态（12 §4）在后台算 | 两边规则一改就容易对不上 | 后端统一算：订单接口同时返回 `customerStatus`（给用户的词）和 `opsStatus`（给后台的词），前端只显示 |

### 1.3 模拟支付（2026-11-12，负责人：不能因为没有商户号就不做支付）

已在分支 `review/admin-workbench-fixes` 实现（提交 `d2572c9`）：

- **环境变量 `PAYMENT_PROVIDER=mock`** 打开模拟支付。只在开发环境可用；体验环境还要设 `MOCK_PAYMENT_IN_TRIAL=1`；正式环境配成 mock 时服务拒绝启动。
- **流程和真实支付一样**：用户 `POST /api/my/orders/{no}/pay` 发起付款 → 后端记一条付款记录、返回 `mock: true` → 小程序弹模拟支付（稿 51）→ 点“支付成功 / 支付失败”调 `POST /api/payments/mock/notify` → 后端按付款记录的金额组一个回调，走和真实回调同一个处理函数：同一回调只处理一次、金额必须对得上、状态按状态机迁移。
- **付款成功**：支付状态变“已支付”，订单从“待确认”自动变“已确认”（S5 一并解决），可以进入制作。订单记 `paymentChannel=mock`，工单上 `mockPayment=true`，后台醒目标出。
- **付款失败**：不改订单状态，用户可以再付一次（状态机里“支付失败”是终点，所以失败只记在付款记录里）。
- **没配支付通道时**：和以前完全一样，订单停在待支付，接口不返回 `pay_order`，模拟回调接口不存在。
- **以后接微信支付**：在 `payments.py` 加 wechat 通道，`create_payment` 换成统一下单，回调先验签再调同一个 `apply_callback`。小程序把模拟弹层换成 `wx.requestPayment`。
- **还没做的**：模拟退款（售后“确认退款”时把支付状态推到已退款），下一步接上。

## 2. 运营侧：订单要有哪些操作按钮

按订单所处的阶段列。“有”是后端已经支持，“缺”要补。

| 阶段 | 按钮（主操作在前） | 后端 |
|---|---|---|
| 任何阶段 | 内部备注（只给后台看）、复制收货信息、看操作记录、联系用户（显示全号） | 内部备注**缺**；其余有 |
| 待支付 | 取消订单（选原因）、改收货地址 | 取消有；改地址**缺** |
| 待制作（已付款） | 开始制作（选负责人）、改地址、取消并退款 | 开始制作有；退款走模拟通道（待接，见 1.3） |
| 制作中 | 去工单（领料、改工序、质检）、改地址、退款（按规则扣除） | 工单、质检有；退款同上 |
| 待发货 | 发货（快递公司 + 单号）、改地址 | 发货有 |
| 已发货 / 运输中 | 改成运输中、标记已签收、标记物流异常、改运单号（填错时） | 改状态有；改运单号**缺**（只能整单重填物流） |
| 物流异常 | 重新发出（新单号）、标记已退回 | 有 |
| 已签收 | 等用户确认；7 天后自动完成 | 自动完成**缺**（S1） |
| 已完成 | 代用户发起售后 | 有（后台建售后单） |
| 售后 | 同意 / 拒绝（写给用户的说明）、确认收到退货、确认退款、补寄（填单号）、改手围重串（**生成新工单**） | 前四个有；补寄填单号、重串生成新工单**缺** |
| 列表 | 按状态筛选、导出表格、批量打印工单 | 导出、批量打印**缺**（前端可先做导出） |

**不做的按钮**：“改成已支付”（付款状态只能由支付回调改）、直接改订单金额、直接改珠序和用料（工单锁定设计快照）。

### 3.1 为什么评价必须审核

- 评价和晒图会公开显示在详情页，属于用户发布的公开内容。按《互联网跟帖评论服务管理规定》等要求，平台要对这类内容建立审核和处置机制，发布者要经过真实身份认证（我们用手机号登录正好满足）。具体合规要求以法务意见为准，记在 README 待确认事项里。
- 微信小程序平台也要求用户生成内容要接入内容安全检查。
- 珠子类目还有一个特别的风险：用户可能在评价里写“戴了转运”“治失眠”这类功效说法，我们自己的文案守住了“只讲寓意”，评价也得守住。

**做法（先审后发）**：
1. 只有登录了手机号、订单已签收的用户能评价。
2. 提交后先过机审：文字走微信文字安全检查，加上我们自己的禁用词表（`kb/data/attributes.json` 的 banned 词，含功效词）；图片走微信图片安全检查（异步回调）。
3. 机审通过的进入“待人审”，**人审通过才公开**；机审不通过的直接打回，告诉用户“内容没有通过审核，改一下再发”。
4. 已公开的可以随时下架，下架要写原因；用户能看到自己的评价被下架了。
5. 所有审核动作记进操作记录。

后台稿新增 A15“评价审核”。

## 4. 商品和定价要不要拆开

**结论：前期不拆，定价放在商品上；但商品按“品种 + 尺寸”两层来展示和管理。**

- 现在一个尺寸就是一个商品（`zt8`、`zt10` 各一条），价格、库存都在这一条上。这本身就是电商里的“一个 SKU 一个价”，86 条的量不需要单独的价格表。
- 真正缺的不是“拆表”，而是这几样：
  1. **按品种分组显示**：列表里“小叶紫檀”一行，展开是 8mm、10mm 两个规格，各自的单价和库存。运营改价时一眼看到同一品种不同尺寸的价差。
  2. **批量调价**：B1 要把 ¥15 手工费并进珠子单价，等于全部 86 条一起改价。需要“按比例 / 加固定金额 / 导入表格”批量改，改前给预览，改后记操作记录。
  3. **成本价（只给后台看）**：可选字段，后台显示毛利，帮负责人定新单价。不给用户看。
  4. **改价不影响已下的单**：订单里已冻结单价（设计快照里有），这条后端已经满足。
- 什么时候再拆：出现“同一颗珠子按等级（A 货 / AA 货）、按渠道、按会员分不同价”，或者要做限时折扣时，再把价格拆成单独的价格规则。到那时促销也放在价格规则里，不改商品。

## 5. 用户设计的手串要不要在后台呈现

**结论：不做“浏览所有用户作品”的页面。**只在这三个地方出现：

| 场景 | 呈现方式 | 理由 |
|---|---|---|
| 下了单的 | 订单详情和工单里，用冻结的设计快照 | 生产要用，已经有了 |
| 分享出去的 | “分享管理”：按链接或作品名查、下架、看举报 | 公开内容要能处置 |
| 运营选款 | **统计**，不看个人：最近 30 天被串得最多的珠子、搭配、颜色 | 帮你挑热门款、定备货，不涉及个人隐私 |

用户没下单、没分享的作品，是用户自己的东西，隐私政策里也没写要拿来用，后台不展示。客服查问题时，可以在“用户查询”里看到他有几条作品，不看内容。

## 7. 知识库要不要在后台留入口，还是用 Obsidian / ima

**结论：知识库继续放在仓库里（`kb/data` 的 JSON），作为唯一来源；后台只做一个只读的“知识库”页。Obsidian 可以用来写调研笔记，ima 不建议用来存知识库。**

理由：

1. **知识库是程序直接读的数据，不是笔记。**每颗珠子的寓意关键词、安全提示、易混珠子、把握程度，都是结构化字段：后端用它给商品补寓意（`kb.enrich`），小程序用它出“每一颗的寓意”，禁用词表也在这里。`kb/validate.py` 会检查每一条（200 种都填完了，有问题 0 条）。换成 Obsidian 或 ima，这些字段就没人校验了，一条写错的寓意或功效词会直接出现在用户手机上。
2. **改动要留痕、要能回退。**放在 git 里，谁改了哪颗珠子的寓意、为什么改，都有记录，出了问题能退回去。
3. **Obsidian 适合当草稿本**：调研、竞品、市场笔记可以在 Obsidian 里写（它本身就是 Markdown 文件，可以直接放在 `kb/market/` 里）。定下来的内容，再整理进 `kb/data`。
4. **ima 不适合**：它是个人知识库加 AI 问答工具，数据放在腾讯那边，没法被我们的程序按字段读取，也做不了校验和版本管理。可以拿它来自己查资料，不要拿它当数据源。

**后台的“知识库”页（只读）要有**：
- 按品种查：寓意、安全提示、把握程度、来源。
- **覆盖检查**：哪些在售商品在用户端不显示寓意，以及原因：没关联知识库，或者对应条目的寓意把握是“低”（不给用户看）。种子数据里有 19 种不显示：16 种是把握低（蜜蜡、草莓晶、红玛瑙、东陵玉等），3 种是金属隔珠隔片（本来没有寓意）。**更正（2026-11-13）**：之前写“19 种没关联知识库”是错的，它们都关联了，原因是把握低。
- 改知识库的方法写在页面上：“提给开发改 `kb/data`，过 `kb/validate.py` 后发布”。

**以后要不要在后台直接编辑知识库**：等运营自己要频繁改的时候再做，而且必须带校验（禁用词、必填字段、把握程度）和审批。现在一个月改不了几次，走 git 更稳。

后台稿新增 A17“知识库（只读）”。

## 9. 需负责人定

| # | 要定的事 | 推荐 |
|---|---|---|
| 1 | 体验环境要不要打开模拟支付（S6 已用模拟支付解决） | 内部测试时打开（`MOCK_PAYMENT_IN_TRIAL=1`）；给外部用户试用时关掉，否则会有人“模拟付款”后要求发货。正式环境在商户号下来前不开放下单 |

| 4 | 评价、晒图、AI 生成内容的合规要求 | 请法务确认：跟帖评论相关规定；AI 配用的是第三方大模型，要不要做生成式 AI 相关的备案或登记 |
| 5 | 批量调价的规则（B1 并入手工费后） | 先用“加固定金额”或“导入表格”两种，不做按比例 |
| 6 | 知识库谁来改 | 先由开发按负责人的意见改 `kb/data`，走校验；Obsidian 作为调研草稿 |
